<Info>
This is a technical reference for developers. If you just want to connect an AI tool, you do not need this: use a [connection](/connect/how-connections-work) instead.
</Info>

Cortex has a small REST API for pushing content into brains from your own scripts and integrations. It is the same surface the automatic capture and webhook features use underneath.

## Base URL and authentication

All endpoints live under `https://api.oncortex.ai/api/v1`. Authenticate with a [service credential](/connect/service-credentials) as a bearer token:

```
Authorization: Bearer ck_your_key_here
```

A credential is scoped to one brain and one access level. Writing endpoints need a read-and-write credential.

## Rate limits

The API and the agent connection endpoint allow **240 requests a minute per credential**, counted in fixed one-minute windows; requests with no credential are counted per client address instead. Over the limit, a request is refused with **429** and a `Retry-After` header giving the number of seconds until the window resets (60 when that cannot be worked out).

A well-behaved client paces itself a little under the limit (the Cortex [command line](/connect/command-line) runs at 200 a minute), waits the number of seconds in `Retry-After` when it does see a 429 before retrying, and saves calls where it can, for example by fetching a brain's page list once at the start of a bulk import rather than reading each page before writing it.

## Push to your default brain

The quickest way to capture something: post to the default inbox, which lands in the credential's brain (or, for a signed-in user, their single writable brain when they have exactly one).

```bash
curl https://api.oncortex.ai/api/v1/inbox \
  -H "Authorization: Bearer ck_your_key_here" \
  -H "Content-Type: application/json" \
  -d '{"filename": "note.md", "content": "The text to capture", "externalId": "unique-id-123"}'
```

Set `externalId` to a stable value so that re-sending the same thing does not create a duplicate.

### Say where the document lives

Four optional fields record where a document lives, so the source record shows the link and later versions are linked as revisions:

| Field | Purpose |
|---|---|
| `canonicalUrl` | The human link (an absolute http or https URL). Anything else is refused with a 400. |
| `provider` | Optional. `sharepoint`, `onedrive`, `gdrive`, `confluence`, `notion` or any name of your own; inferred from the link's host when omitted. |
| `providerItemId` | Optional. The stable id at the provider (a Graph drive item id, a Drive file id, a Confluence page id). Parsed from Google Drive links when omitted. |
| `version` | Optional. The etag or version at fetch time. Without it, a changed document still counts as a new version, by its content. |

When you give a reference and no `externalId`, Cortex derives one as `{provider}:{itemId}@{version}`, so re-sending the same version is a no-op and a new version becomes a new item linked to the earlier one. The response of a GET on the new item carries `revisionOf` (the earlier item, its status and the pages it was filed to) and `revisionDiff`, a line diff of the two extractions.

### Send the file itself

A JSON body can carry the document as base64 instead of text:

```bash
curl https://api.oncortex.ai/api/v1/inbox \
  -H "Authorization: Bearer ck_your_key_here" \
  -H "Content-Type: application/json" \
  -d '{"filename": "brief.docx", "contentBase64": "<base64>", "canonicalUrl": "https://sopro.sharepoint.com/sites/cs/brief.docx", "version": "3"}'
```

`contentBase64` and `content` are mutually exclusive. The decoded size is capped at 10 MB on this route; larger files go as multipart form data, up to 50 MB, where the same four fields are accepted as form fields. The same rules apply to your agent's `upload_to_inbox` tool.

Optional query parameters:

- `?claim=true` marks the item as held by the agent that is calling: it arrives as `in_progress` with `claimedBy` set to `agent`, and Cortex's own filer never picks it up; the caller is expected to write the pages and archive the item. Without it, the item arrives `pending` and Cortex files it under the workspace's monthly ingestion limit. A held item nobody finishes within 30 minutes moves to `needs_review`. See [how ingestion is paid for](/filing/how-ingestion-is-paid-for).
- `?brain={slugOrId}` names a destination brain explicitly (it must be one the credential can write to; a brain-scoped credential can only name its own brain).
- `?path={folder}` suggests where the content should file. It is recorded as a hint for the filing pass, not an order; the content itself can never choose its own destination.
- `?partition={key}` names the client (or site, or matter) in a [partitioned brain](/brains/partitions). An unknown or archived key is refused with a 422 that lists the existing keys. Without it, the attendee emails decide, or the item waits as "needs a client".
- `?skill={name}` (or `skill` in the JSON body or as a form field) pins the filing skill: `ingest`, `ingest-meeting`, `ingest-doc`, `ingest-conversation` or `ingest-email`. A deliberate upload that names its skill skips the automatic filer's "is this worth filing" check and goes straight to that skill; leave it out for ambient captures (a session hook, say) so the check still runs. A name that is not a skill is refused with a 400 that lists the skills. The same `skill` argument is on your agent's `upload_to_inbox` tool.
- `?retain=none` (or `retain` in the JSON body or as a form field) asks for the item's body not to outlive its filing. See [retention](#retention-ask-for-the-body-not-to-be-kept) below.

### Retention: ask for the body not to be kept

By default an inbox item's body is kept: archived with the item, readable in the brain's Sources, downloadable, and available to replays. Any caller can ask for the opposite, for content that should be read once and then gone:

| Route | How to ask |
|---|---|
| `POST /api/v1/inbox` and `POST /api/v1/brains/{brainId}/inbox` | `retain` in the JSON body, `?retain=none` on the address, or `retain` as a multipart form field |
| `POST /api/ingest/{brainId}` (a [webhook source](/reference/webhooks)) | `?retain=none` or the `X-Ingest-Retain: none` header |
| An agent's `upload_to_inbox` tool | the `retain` argument |

`none` is the only value that does anything; anything else leaves the item on the default. With it, the body exists only while the item waits to be filed and is destroyed the moment filing ends, whether the item is archived, rejected, deleted or closed unfiled after seven days. What survives is the stub: the filename, the source reference, the content hash, the external id, the pages it was filed to, the dates and the log.

A `kind: email` contract is given `retain: none` at the door whether or not the caller asks, along with the `ingest-email` skill and the [routing rules](/reference/email-contract) that go with mail.

Afterwards, `GET`s on the item report `retention` (`none` or `keep`) and `bodyDestroyedAt`; `GET /api/v1/brains/{brainId}/inbox/{itemId}/download` answers **410** with "Not retained: the body of this item was destroyed when filing ended"; an agent's `get_source_file` answers with an error instead of the file; and the item's Sources record shows "Body not kept" with the link to the original in place of the download.

## Work with a specific brain's inbox

| Do this | Request |
|---|---|
| List inbox items | `GET /api/v1/brains/{brainId}/inbox` (optionally `?status=`) |
| Get one item | `GET /api/v1/brains/{brainId}/inbox/{itemId}` |
| Upload an item | `POST /api/v1/brains/{brainId}/inbox` |
| Update an item's status | `PUT /api/v1/brains/{brainId}/inbox/{itemId}/status` |
| Archive an item | `POST /api/v1/brains/{brainId}/inbox/{itemId}/archive` |
| Delete an item for good | `DELETE /api/v1/brains/{brainId}/inbox/{itemId}` (Admin on the brain; removes the item, its original file and its extracted text; pages filed from it keep source lines that now point at nothing) |
| Download the original | `GET /api/v1/brains/{brainId}/inbox/{itemId}/download` (add `?extracted=true` for the extracted text; **410** when the item's body was not retained and has been destroyed) |

Uploads accept either a JSON body (`filename`, `content` or `contentBase64`, optional `externalId`, `targetFolder`, `skill` and the four reference fields above) or multipart form data for binary files, up to 50 MB, with `canonicalUrl`, `provider`, `providerItemId`, `version` and `skill` as form fields. The `?path={folder}`, `?skill={name}` and `?claim=true` options work here too. Items carry `status`, `claimedBy` (`agent`, `runner` or null: who holds an item that is being filed), `skillHint` (the pinned skill, or null), `sourceReference`, `supersedesItemId` and `supersededByItemId`; a GET on one item adds `revisionOf` and `revisionDiff`.

## Upload a file with a one-time token

This is the route a connected agent uses to get a file from its shell into the inbox without the bytes passing through the conversation. The agent asks Cortex for a token with its `create_upload_token` tool (Write on the brain), naming the filename, the brain, the filing skill and, optionally, where the document lives. The token starts with `ut_`, is good for **one brain, one file, one use, for 15 minutes**, and can do nothing else; Cortex stores only a hash of it. The tool returns a ready-made `curl` line:

```bash
curl -X PUT https://api.oncortex.ai/api/uploads \
  -H "Authorization: Bearer ut_your_token_here" \
  --data-binary @acme-brief.pdf
```

The body is the file, either raw or as the first part of a multipart form (`POST` is accepted as well as `PUT`, and the token may be sent in an `X-Upload-Token` header instead). Up to 50 MB. The item is created held by the agent (`in_progress`, `claimedBy: "agent"`) with the skill and source reference pinned, and the response carries what the agent needs next:

| Field | Meaning |
|---|---|
| `id`, `brain`, `filename`, `status`, `claimedBy` | The new inbox item. |
| `sourceUrl` | The item's citable address, for the source line on every page. |
| `extracted`, `extractionNote` | Whether Cortex could extract text (PDF, Word, PowerPoint, plain text), and a sentence saying so, or saying that it could not (a scan, an image, a format Cortex does not open). |
| `extractedText`, `extractedTextTruncated` | The document's text. The first 200,000 characters are inline; when there is more, `extractedTextTruncated` is true and the rest is on the item (`GET .../inbox/{itemId}`). |
| `revisionOf`, `revisionDiff` | When the file is a new version of a document already filed: the earlier item, its status and the pages it fed, and a line diff of the two extractions. |
| `note` | One line on what to do next. |

An unknown or malformed token is a bare **401**. A token that has already been used, or has expired, is a **410** with a message saying which. A refused upload (an empty body, say) is a **400**.

```bash
# Upload text to a named brain's inbox
curl https://api.oncortex.ai/api/v1/brains/{brainId}/inbox \
  -H "Authorization: Bearer ck_your_key_here" \
  -H "Content-Type: application/json" \
  -d '{"filename": "report.md", "content": "..."}'
```

## Inbound mail

This is where forwarded mail arrives. A brain marked as its owner's personal brain can be given an inbound address on its Connect page, shaped `{brain-slug}-{24 random characters}@in.oncortex.ai`. Mail sent to it reaches Cortex through a mail relay, which posts the raw message here and decides nothing:

```
POST https://api.oncortex.ai/api/inbound/email
```

| Header | Value |
|---|---|
| `X-Inbound-Secret` | The shared secret, compared in constant time. Wrong or missing is a bare **401** with no body. |
| `X-Inbound-To` | The envelope recipient: the brain's inbound address. Required; without it, **400**. |
| `X-Inbound-From` | The envelope sender, as the forwarding mailbox rewrote it. |
| Body | The raw RFC 822 message, up to 10 MB. |

An authenticated post always answers **200** with `{ "outcome", "itemId", "reason" }`, whatever happened to the message, so that the relay never bounces anything and the address cannot be used to find out whether a brain exists:

| `outcome` | What happened |
|---|---|
| `accepted` | The message became an inbox item, pinned to `ingest-email` and waiting to be filed. `itemId` names it. |
| `duplicate` | The same message had already been delivered. Nothing new was created. |
| `refused` | The address exists but the message may not enter, with `reason` saying why: the brain is not marked as anyone's personal brain, the sender is not a verified mailbox of its owner, or the sending domain passed neither SPF nor DKIM. The refusal is counted on the brain, with the date and the sender's domain, and the message is not stored. |
| `unknown-address` | No brain owns that address, or it has been rotated or removed. |
| `confirmation` | Gmail's "confirm this forwarding address" mail. The code is kept for the brain's Connect page and the message is never filed. |

A post that arrives while no inbound secret is configured answers **503**.

Cortex builds the [email contract](/reference/email-contract) from the message itself: who forwarded it (the forwarding headers, the envelope sender with the usual rewriting undone, then the From header, each checked against the owner's verified addresses), the original sender and subject (from the forwarded block for a message forwarded by hand, or from the headers for one forwarded by a rule), the participants, and the new message's text with quoted history stripped. Attachments are dropped and their names carried through. The item that results has retention `none` like any mail item.

## Pages, timelines and the graph

The page endpoints take a brain-scoped credential and the page path as `?path=`. Writes need a read-and-write credential.

| Do this | Request |
|---|---|
| List pages, or read one | `GET /api/v1/brains/{brainId}/pages` (`?path=` for one page, with its markdown and its `outline`; read it in pieces with the parameters below) |
| Create or replace a page | `PUT /api/v1/brains/{brainId}/pages` with `{ "path", "markdown", "expectedVersion" }` |
| Add to one part of a page | `PATCH /api/v1/brains/{brainId}/pages?path=` with `{ "operation", "section", "content", "position" }` (append to or replace a section, append to the page, set frontmatter keys) |
| Read a page's timeline | `GET /api/v1/brains/{brainId}/pages/timeline?path=&limit=` (the dated lines of its Timeline section, newest first) |
| Add a timeline line | `POST /api/v1/brains/{brainId}/pages/timeline?path=` with `{ "text", "date"? }` (today when omitted) |
| Move or rename a page | `POST /api/v1/brains/{brainId}/pages/move` with `{ "fromPath", "toPath" }` (links to the old name are rewritten; refused when the target exists) |
| Delete a page | `DELETE /api/v1/brains/{brainId}/pages?path=` |
| What changed since last time | `GET /api/v1/brains/{brainId}/changes?since=&limit=` (keep the returned `nextCursor` and pass it back as `since`) |
| Who links to a page | `GET /api/v1/brains/{brainId}/graph/backlinks?path=` |
| Pages within a few hops | `GET /api/v1/brains/{brainId}/graph/traverse?path=&depth=&limit=` (depth 1 to 3) |
| Check names before linking | `POST /api/v1/brains/{brainId}/graph/resolve` with `{ "refs": ["a slug", "a title", "a/path.md"] }` (the page each would link to, or near misses) |
| Search | `GET /api/v1/brains/{brainId}/search?q=&mode=` (`exact`, `semantic` or `hybrid`) |

An edit sent with a stale `expectedVersion`, or one that lands while someone else is saving, is refused with a 409 and the message "This page was changed by someone else. Reload and try again."; read the page again and resend.

### Reading a page in pieces

A single-page read (`?path=`) takes four more parameters, so a caller that found the right passage by search is not handed the whole page for it:

| Parameter | Effect |
|---|---|
| `section={heading}` | Only that section of the page, matched by heading; the response's `section` names the heading that matched. An unknown heading is refused with the page's headings listed. |
| `outline=true` | Headings only, no body. |
| `maxChars={n}` | Only the opening, cut at that many characters. |
| `whole=true` | The whole body even when the page is long. |

Every read returns `outline`, the page's headings in order. A page over **20,000 characters** comes back cut at that point, with its outline and a note, unless `whole=true` is passed.

### What a search hit carries

Each hit in a search response carries `section`, the text of the chunk that matched (up to 1,500 characters), and `outline`, the page's headings in order, alongside the path, title, snippet and score. Most questions can be answered from `section` alone; when more is needed, read the page with `section={heading}` rather than whole.

## Your personal brain

One brain per member per workspace is marked as that member's personal brain: the default destination for an agent's writes when it can reach several brains, and reported as `personal` in the brain list an agent sees.

| Do this | Request | Role |
|---|---|---|
| Mark a brain as yours | `POST /api/v1/brains/{brainId}/personal` (empty body) | Owner |

The mark belongs to the signed-in user, so this needs a user's token (a connection or the [command line](/connect/command-line#marking-your-brain-as-yours)), not a service credential. Marking a second brain moves the mark; any other brain carrying it for you loses it. The brain Cortex created for you when you joined carries it already. There is no Settings switch for this yet.

## Partitions

In a [partitioned brain](/brains/partitions) the clients (or sites, or matters) are managed here as well as on the Clients page. Roles are the caller's role on the brain: a service credential carries the role it was issued with, so a Write credential can push and assign, an Admin credential can manage partitions, and only an Owner credential or an owner's connection can purge.

| Do this | Request | Role |
|---|---|---|
| List, searchable | `GET /api/v1/brains/{brainId}/partitions?query=&status=` | Read |
| Get one | `GET /api/v1/brains/{brainId}/partitions/{key}` | Read |
| Create with its folder | `POST /api/v1/brains/{brainId}/partitions` with `{ "name", "key"?, "domains"?, "aliases"?, "externalRef"? }` | Admin |
| Update | `PUT /api/v1/brains/{brainId}/partitions/{key}` | Admin |
| Archive or restore | `POST /api/v1/brains/{brainId}/partitions/{key}/archive` or `/restore` | Admin |
| Import many | `POST /api/v1/brains/{brainId}/partitions/import` with an array of the same fields | Admin |
| Purge, permanently | `DELETE /api/v1/brains/{brainId}/partitions/{key}?purge=true` (refused without the flag; the partition must be archived) | Owner |
| Assign an inbox item | `POST /api/v1/brains/{brainId}/inbox/{itemId}/partition` with `{ "key", "rememberDomains" }` | Write |

Inbox listing takes `?partition={key}` and `?unassigned=true`. Search takes `?partition=`, `?folder=` and `?includeArchived=true` (archived partitions are left out of results unless asked for).

## Members

A brain's access list can be managed here as well as on its Members page, so onboarding a person or an agent can be scripted. The caller needs Admin or Owner on the brain: a service credential counts with the role it was issued, so a read-and-write credential is refused with a 403 and can never widen anyone's access. Only workspace members can be granted (invite them to the workspace first); one grant per person; the last Owner cannot be demoted or removed. Name the person by their user id or their email.

| Do this | Request | Role |
|---|---|---|
| List members | `GET /api/v1/brains/{brainId}/members` (user id, email, display name, role, when granted) | Admin |
| Grant access | `POST /api/v1/brains/{brainId}/members` with `{ "email" or "userId", "role" }` (`Read`, `Write`, `Admin` or `Owner`; `Read` when omitted) | Admin |
| Change a role | `PUT /api/v1/brains/{brainId}/members/{userId}` with `{ "role" }` (the email works in place of the id) | Admin |
| Revoke access | `DELETE /api/v1/brains/{brainId}/members/{userId}` | Admin |

A grant for someone who already has access is refused with a 409; a grant for someone who is not in the workspace, a demotion of the last Owner, or an unknown role is a 400 with the reason. There is no agent tool for any of this, on purpose: an agent in a conversation cannot add or remove members.

## Receiving from third-party tools

If instead you want an outside tool to push into Cortex (rather than calling the API from your own code), use the [webhook route](/reference/webhooks), which is designed for that and has its own authentication.
